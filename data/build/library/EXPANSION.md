# Library-usage dataset expansion (v1 -> v2)

The staged plan for deepening `data/train/library_usage/` and connecting it to the
**LibReuseBench** eval benchmark in `benchmark/`. Kept here so the reasoning survives between
work sessions; see [../../README.md](../../README.md) for how the pipeline is run.

## Why

v1 is deterministic and shallow: 50 categories x ~2 tasks x 7 wordings = 714 rows, generated by
**5 templates and 2 repo contexts**, with the LLM seam (`augment.py`) inert. Two problems:

**1. It barely overlaps the benchmark's domains.** Clustering all 129 shipped LibReuseBench test
problems by *which library call does the real work in `ground_truth.gold_extlib`*:

| benchmark skill | problems | covered in v1? |
| --- | --- | --- |
| feature scaling (z-score / min-max) | 17 | no category at all |
| pattern extraction from text | 15 | no |
| descriptive statistics | 13 | no |
| value counts / modes | 9 | no |
| tabular CSV in/out | 8 | `csv-excel`, but file-oriented |
| numpy reductions & ufuncs | 7 | `numerics`, but only matmul + regression slope |
| timezone conversion | 7 | `timezones` |
| text vectorisation (TF-IDF, counts) | 6 | no |
| correlation / statistical tests | 5 | `hypothesis-testing` |
| stopwords & word frequency | 5 | `nlp-tokenize` |
| groupby aggregation | 4 | no |
| date parsing | 4 | `datetime` |
| categorical encoding | 4 | no |
| dataframe reshaping | 4 | no |
| pairwise distances | 3 | no (`geo-distance` is lat/lon only) |
| combinatorics | 3 | no |
| clustering, regression, imputation, FFT, primes, SQL, crypto, kNN, string similarity | 1-2 each | partly |

Only **10 of the 50 v1 categories** are exercised by the benchmark at all. The library counts agree:
`gold_extlib_packages` is numpy 61, pandas 51, regex 15, python-dateutil 10, scipy 7, pytz 4,
nltk 4, scikit-learn 3, more-itertools 2, then singletons.

**2. It asks in the wrong register.** Every v1 prompt is `"How do I X in Python?"`, asking for a
function. Every benchmark prompt is a stdin/stdout exercise statement with `Input format:`,
`Output format:` and one `Example:` block.

## What v2 changes

- **+16 categories** derived from the benchmark clustering above, and **+25 tasks** deepening the
  10 existing categories the benchmark already reaches (plus a handful more added later while
  cross-checking a subsequent benchmark expansion - see the git history for `tasks.yaml`).
- **3 prompt types x 2 sources.** Every task is now asked in 3 modes - `repo` (existing), `simple`
  (renamed from `bare`), and `script` (new, stdin/stdout, reminiscent of the benchmark's wording)
  - each from 2 sources: a deterministic `template` and a claude-generated wording. Every task
  gets exactly one row per (mode, source): **6 rows/task** in steady state, 3 rows/task
  (template-only) while a claude cache is still empty. This absorbs what was originally planned
  as a standalone `benchmark` mode (LLM-written statements) into `script`'s claude-generated
  variant, and adds a claude-generated variant to `repo` too, which the original plan didn't have.
- **The LLM seam turned on** — real claude-generated wordings, cached to `simple_prompts.json`,
  `script_prompts.json` and `repo_prompts.json` (retiring the old `phrasings.json`).
- **No more row-weighting by `benchmark_aligned`.** Every task gets the same 6 rows regardless of
  alignment - the flag still exists and still drives which categories/tasks got deepened (Stage
  1), it just no longer multiplies row counts inside `build.py`.
- **repo-mode picks one repo per task**, not every repo. A new `repo_hint` field on every
  taxonomy.yaml category names which of the 2 vendored python repos (`pytoolbox`, `python-api`)
  fits that category best; `build.py` sets a task's repo-mode rows there instead of cross-
  producting every task against every repo.

Target: **194 tasks** (confirmed, Stage 1 complete), 66 categories, **1164 rows** once all three
claude caches are populated (582 rows, template-only, today).

Nothing from v1 is removed or reworded. Existing tasks keep their exact `task` string, which is
what `split_disjoint_test` groups on, so the held-out-task guarantee is unaffected.

## Stages

Delivered in three reviewable stages, with a revision step between each.

### Stage 1 - categories and tasks

- `taxonomy.yaml`: append the 16 new categories; add `benchmark_aligned: true` to those and to the
  10 existing aligned ones (`csv-excel`, `numerics`, `hypothesis-testing`, `nlp-tokenize`,
  `timezones`, `datetime`, `crypto-hashing`, `fuzzy-matching`, `geo-distance`, `sql-builder`) -
  26 aligned of 66. Absent means false, so the other 40 need no edit.
- `tasks.yaml`: +64 tasks (4 per new category) and +25 deepening the aligned existing ones.

Two categories need care, because the honest solution is stdlib and the reward would otherwise be
teaching a distinction without a difference:

- `regex-text-extraction` - the benchmark's `regex` golds are functionally identical to stdlib
  `re`. Tasks aim at the dataframe/structured framing (`Series.str.extract`, log lines into a
  table), not "prefer `regex` over `re`".
- `combinatorics` - stdlib `itertools` is the honest answer, so tasks aim at what `more_itertools`
  and `sympy` genuinely add (distinct combinations, subset products, ranked selections).

Checkpoint: the build still runs unchanged (the new key is ignored) and the audit reports 66
categories.

**Status: complete** - 66 categories, 194 tasks, `benchmark_aligned` flags all in place. The
`repo_hint` field described in Stage 3 below is a later, incremental addition on top of this
already-finished stage, not part of its original scope.

### Stage 2 - the LLM layer

- New `data/build/llm.py`: a small Anthropic client modelled on
  `benchmark/pipeline/generation.py` (`complete`, `complete_json` with structured outputs,
  model from `EVAL_DATASET_MODEL`). Separate from the benchmark's client so `data/` and
  `benchmark/` stay independent.
- `augment.py` is rewritten with three generators - `simple` (BigCodeBench-style function-stub
  prompts), `script` (a LibReuseBench-register stdin/stdout statement, reusing the constraint
  list from `benchmark/pipeline/03_rewrite.py` so it reads like the benchmark's, adapted since
  our tasks are one-line descriptions rather than full seeded problems), and `repo` (a natural
  request framed inside the task's `repo_hint` repo) - each with its own committed cache
  (`simple_prompts.json` / `script_prompts.json` / `repo_prompts.json`) and a CLI
  (`python data/build/library/augment.py --type simple|script|repo|all`) to regenerate them
  offline. Generated for **every** task (not just `benchmark_aligned` ones, now that row count
  no longer depends on alignment).
- Library-name leaks are rejected with a locally-duplicated 25-term blocklist (not imported, to
  keep `data/` independent of `benchmark/` - see `augment.py`'s `_LIBRARY_NAME_TERMS`, kept in
  sync by hand with `benchmark/libreusebench/libraries.py::_LIBRARY_NAME_TERMS`) as well as the
  category's own `seed_libraries`.

All three caches are committed, so `build.py` stays deterministic and needs no API key.

Checkpoint: sample all three caches by hand for quality and leaks.

### Stage 3 - modes, wiring and plumbing

- `taxonomy.yaml` gains `repo_hint` on every category, naming which of the 2 vendored python
  repos (`pytoolbox`, `python-api`) its repo-mode rows are set in.
- `templates.yaml`'s `bare` mode is renamed `simple`, and gains a new `script` mode - 2 templates
  each, contextless, matching `repo`'s existing 2. `build.py` deterministically (seeded) picks
  ONE template per task per mode via a new `_pick_one` helper, instead of emitting a row for
  every template.
- `build.py` also gains a `_task_stdio` helper (the tasks are written function-style - "and
  return the result" - which reads wrong inside a stdin/stdout ask), the `repo_hint`-based
  single-context lookup (replacing the old every-task-x-every-repo cross product), and one claude
  row per mode per task when the matching cache has an entry. `DATASET_VERSION` becomes `v2`.
- Downstream: nothing needed - `audit.py`, the eval scorer, and the Fireworks representative
  sampler all bucket `phrasing_mode` generically by whatever string is present, with no hardcoded
  mode list, so the `bare`->`simple` rename and the new `script` mode need no changes there.

**Rows per task** - uniform, no `benchmark_aligned` weighting:

| mode | source | rows/task |
| --- | --- | --- |
| `repo` | 1 (of 2) templates, in the task's `repo_hint` repo | 1 |
| `repo` | claude (`repo_prompts.json`) | 1 (once generated) |
| `simple` | 1 (of 2) templates | 1 |
| `simple` | claude (`simple_prompts.json`) | 1 (once generated) |
| `script` | 1 (of 2) templates | 1 |
| `script` | claude (`script_prompts.json`) | 1 (once generated) |
| | | **6** |

194 tasks x 6 = **1164 rows** once all three caches are populated; 194 x 3 = **582 rows** while
they're still empty (template-only, today).

## Known caveats

- **Five benchmark problems reward performative imports.** `LRB/T063` and `LRB/T095` do all their
  real work with stdlib string methods wrapped in a decorative `np.array(...)`; `T086`, `T097` and
  `T113` build a trivial `DataFrame` or `np.vectorize` only to hand back a pure-python result.
  The reuse metric is "an external import is present and used", so these score as reuse without
  any. Worth revisiting the benchmark's stage-02 filter separately.
- **The two response parsers disagree.** `src/response/parser.py` strips `<think>` blocks and
  returns empty with no fences; `benchmark/libreusebench/libraries.py` does neither and falls back
  to the whole response. The training reward also aggregates reuse across *all* code blocks while
  the benchmark inspects only the longest - so training rewards a pattern the benchmark measures
  more narrowly. Out of scope here, but it caps how well training rates predict benchmark rates.
- **The available-libraries system prompt is deliberately unused.** Library-usage prompts must
  never advertise a library list, so `libraries_requirements_file` stays unset in
  `config/training.yaml`.
